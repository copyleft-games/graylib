* Audio System
:PROPERTIES:
:CUSTOM_ID: audio-system
:END:
This document covers the audio types added in Phase 4: audio device, sound effects, and streaming music.

#+begin_quote
*raylib 6.0 pan behavioral change.* Sound/music/stream pan is now =[-1.0 .. 1.0]= end-to-end: =-1.0= = full left, =0.0= = centered, =1.0= = full right. graylib's public pan API was always =[-1.0 .. 1.0]=; previously it internally converted to raylib's old =[0 .. 1]= convention before forwarding. raylib 6.0 adopts the =[-1.0 .. 1.0]= convention directly, so that internal conversion has been *removed*. The public API is unchanged, but if you were relying on the (undocumented) old internal mapping, the raw value now passes straight through. Affected setters: =grl_sound_set_pan()=, =grl_music_set_pan()=, and =grl_audio_stream_set_pan()=.

#+end_quote

*** Backends
:PROPERTIES:
:CUSTOM_ID: backends
:END:
raylib opens its device through miniaudio, which tries its backends in a fixed order: PulseAudio before ALSA on Linux.  miniaudio 0.11.24 (the one raylib 6.0 bundles) crashes in its PulseAudio backend now and then: in =ma_device_init()= it asks libpulse for the default sink's info, and when libpulse answers that lookup with an error (=eol= < 0, no info), miniaudio's callback ignores the error and dereferences the =NULL= info.  PipeWire's pulse server does that under load, when many clients open streams at once (reproduced: 16 processes opening and closing the device in a loop all crashed within 60 opens, =SIGSEGV= in =ma_context_get_device_info_sink_callback__pulse=).  This miniaudio has no native PipeWire backend.

graylib therefore chooses the order itself.  raylib's =InitAudioDevice()= takes no backend list and raylib's sources are not changed, so graylib makes miniaudio's PulseAudio backend fail at once by pointing =PULSE_SERVER= at a socket that does not exist for the duration of the call (restored right after); miniaudio then moves on to ALSA, which reaches PipeWire through pipewire-alsa (or PulseAudio through its ALSA plugin).  PulseAudio, in miniaudio's own order, is only tried when ALSA opened nothing.

| =GrlAudioBackend= | =GRL_AUDIO_BACKEND= | Order |
|---------------------------------+---------------------------------+------------------------------------------------------------|
| =GRL_AUDIO_BACKEND_AUTO= (default) | =auto= | ALSA, then PulseAudio (miniaudio's order) if ALSA fails |
| =GRL_AUDIO_BACKEND_ALSA= | =alsa=, =pipewire= | ALSA only |
| =GRL_AUDIO_BACKEND_PULSEAUDIO= | =pulse=, =pulseaudio= | miniaudio's order: PulseAudio first (the old behaviour) |
| =GRL_AUDIO_BACKEND_NONE= | =none=, =off=, =null=, =0= | no device: the game runs silently |

#+begin_src C
/* before the device opens (the first grl_audio_device_get_default ()) */
grl_audio_device_set_preferred_backend (GRL_AUDIO_BACKEND_ALSA);

GrlAudioBackend backend;
if (grl_audio_backend_parse (user_setting, &backend))
    grl_audio_device_set_preferred_backend (backend);
#+end_src

- The environment variable =GRL_AUDIO_BACKEND= wins over the preference set in code (=grl_audio_device_get_preferred_backend()= returns the effective one); an unknown value logs a message and means =auto=.
- The choice applies the next time the device opens; an open device is not reopened.
- On macOS, Windows, Android and the web there is no choice to make: =auto=, =alsa= and =pulseaudio= all open the platform's own backend; =none= still turns audio off.
- *Failure is not fatal.*  When no backend opens a device, =grl_audio_device_init_audio()= returns =FALSE= and logs a message naming the backend and =GRL_AUDIO_BACKEND=; sounds and music fail to load or stay inert and every call on them is a no-op, so a game keeps running without sound.
- Cost: opening through ALSA took ~0.2 s here against ~0.08 s through PulseAudio (once per run).  Under a private =XDG_RUNTIME_DIR= without the PipeWire socket, ALSA's PipeWire plugin waits a long time for it; set =PIPEWIRE_RUNTIME_DIR= (see libregnum's =docs/performance.org=).
- Caveat: =setenv()= is not thread-safe against a concurrent =getenv()= on every libc; graylib changes the variable only while the device opens, which games do at start-up.

Tests: =tests/test-audio-backend.c= (=/audio-backend/parse=, =preference=, =none= headless; =/audio-backend/init-stress= opens and closes the device 12 times through the default order when an audio server is reachable).

*** The audio thread
:PROPERTIES:
:CUSTOM_ID: audio-thread
:END:
raylib has one audio lock (=AUDIO.System.lock=).  Its mixer holds it for every device period, with graylib's stream callbacks and processors running inside it, and =UpdateMusicStream()= holds it for a whole sub-buffer decode (up to ~2 ms of Vorbis or MP3).  Every raylib call that changes a voice (=PlaySound()=, =SetSoundVolume()=, =IsSoundPlaying()=, ...) takes the same lock, so a game-thread call that landed in such a window used to wait for it: up to 5.5 ms per call in libregnum's =sfx-calls= benchmark, 12 ms under a slow stream callback.

While the device is open graylib runs one thread, =grl-audio= (=src/audio/grl-audio-queue.c=), and the game thread's audio calls become commands for it:

| What | Where it runs |
|------+---------------|
| =GrlSound=: =play=, =stop=, =pause=, =resume=, =play_multi=, =stop_multi=, =set_volume=, =set_pitch=, =set_pan=, =update=, unload | queued |
| =GrlMusic= with background streaming: the same, plus =seek=, =set_looping=, refills | queued |
| =GrlAudioStream= with a callback: =play=, =stop=, =pause=, =resume=, =set_volume=, =set_pitch=, =set_pan=, unload | queued |
| =GrlMusic= without background streaming, =GrlAudioStream= without a callback | direct, as before (their data path, =grl_music_update()= / =grl_audio_stream_update()=, takes the lock on the caller's thread anyway, and the calls must stay in order with it) |
| Loading, aliases, processors, setting a stream callback, the master volume | direct (setup-time calls; the master volume is an atomic in miniaudio, no lock) |

- *Queue.*  A lock-free list (a Treiber stack: a compare-and-swap push, the thread takes the whole list with another and reverses it), so each producer's commands run in the order it pushed them, and calls on several objects stay in order with each other.  A push never waits on a lock: commands are recycled (the thread hands applied ones back on a second lock-free list, a producer takes that list into a thread-local cache in one exchange), so the steady state neither mallocs nor frees, and nothing is freed across threads.  The thread sleeps on a condition variable; a producer wakes it only when it announced it is about to sleep (Dekker-style atomics), signalling under a =trylock= when it gets the lock and without it otherwise, and the thread never sleeps longer than 20 ms, which bounds the one rare lost wake-up (a signal in the few instructions between the thread's last check and its wait).
- *Getters stay coherent.*  =grl_sound_is_playing()=, =grl_music_is_playing()=, =grl_music_get_time_played()= (background) and =grl_audio_stream_is_playing()= (callback) read a mirror and never take raylib's lock.  A call that changes whether a voice plays carries a serial and the state it will leave (=play= -> playing, =stop= / =pause= -> not, =resume= -> what it was when paused); until the thread has applied it and read raylib's state back, the getter reports that prediction, then raylib's state.  A queued =seek= or =stop= reports its position at once.  The thread re-reads every playing voice about every 5 ms, which is how a sound's natural end shows up (within ~5 ms of it).
- *Refills.*  Background music refills are this thread now (the old =grl-music= thread is gone): =UpdateMusicStream()= for every playing background music about every 5 ms.
- *Lifetimes.*  Commands hold a reference to a small refcounted voice the object embeds, not to the GObject, so the thread never runs a finalize: dropping a sound queues its unload after its other calls (an alias before its source when they are dropped in that order) and returns.
- *Latency.*  A queued call reaches raylib as soon as the thread runs (microseconds when the lock is free, else when the mixer or a decode releases it), which is no later than the next device period would have heard it anyway.
- *Blocking calls left.*  Switching background streaming off, and removing or replacing a stream's callback, wait for what is queued (=grl_audio_queue_flush()=, internal) so the direct calls after them stay in order.  =grl_audio_device_close()= applies every queued command, then joins the thread, then closes raylib's device.
- *Inline without a device.*  Before the device opens (or after it closes) commands run at once on the caller's thread and getters ask raylib, as before.

Measured (libregnum =lrg-bench -s sfx-calls=, 8 sounds' volume / pitch / pan / is-playing / retrigger calls every 3 ms frame while a Vorbis track decodes and a MIDI synth renders; Xvfb, 1000 frames): per-call max 5.5 ms -> tens of µs; see libregnum's =docs/performance.org=.

Thread safety: =make -C tests tsan TSAN_CC=clang= (or gcc with libtsan installed) builds the audio sources and =test-audio-queue=, =test-audio-backend=, =test-music= and =test-audio-stream= with ThreadSanitizer (raylib uninstrumented, its pthread locks seen through TSan's interceptors); =tests/tsan.supp= suppresses only the system audio stack (ALSA, PipeWire, PulseAudio) and raylib's =CloseAudioDevice()=, which destroys its mixing mutex before it stops the device thread.

Tests: =tests/test-audio-queue.c= (=/audio-queue/lock-hammer=: a stream callback holds raylib's lock 6 ms of every period while ~62000 sound calls are timed; a direct raylib call is checked to wait for it (6-12 ms), graylib's must not: no call may give up the CPU voluntarily (=getrusage(RUSAGE_THREAD)= voluntary context switches, i.e. no futex wait on any lock), the calls the scheduler did not preempt stay under 1 ms (measured: median 0.1 µs, p99 3 µs, max 20-70 µs) and p99 under 0.2 ms; and =is_playing()= must follow play / stop / pause / resume at once and see a 50 ms sound end; =/audio-queue/release-order=: objects dropped with calls queued, then the device closed).

*** Stream Updating (CRITICAL!)
:PROPERTIES:
:CUSTOM_ID: stream-updating-critical
:END:
*You MUST call =grl_music_update()= in your main loop while music is playing:*

#+begin_src C
while (!grl_window_should_close (window))
{
    /* Update music stream buffers - REQUIRED! */
    grl_music_update (music);

    /* Rest of your game loop... */
    grl_window_begin_drawing (window);
    /* ... */
    grl_window_end_drawing (window);
}
#+end_src

Without calling =grl_music_update()=, music will stutter or stop, unless the music streams in the background (next section).

*** Background Streaming
:PROPERTIES:
:CUSTOM_ID: background-streaming
:END:
=grl_music_update()= decodes on the caller's thread: raylib's =UpdateMusicStream()= decodes a whole sub-buffer each time the device has consumed one, 1-3 ms of Vorbis or MP3 every few frames, all of it inside raylib's audio lock.  A background-streamed music is refilled by graylib's streaming thread instead:

#+begin_src C
grl_music_set_background_streaming (music, TRUE);   /* or the "background-streaming" property */
grl_music_play (music);
/* no grl_music_update () needed; calling it does nothing */
#+end_src

| Aspect | Behaviour |
|--------+-----------|
| The thread | graylib's audio thread ([[#audio-thread][the audio thread]]), started when the device opens; refills every playing background music about every 5 ms with =UpdateMusicStream()= |
| Cost when idle | none: with no voice playing and nothing queued the thread sleeps on a condition variable |
| Control calls | =play=, =stop=, =pause=, =resume=, =seek=, =set_looping=, =set_volume=, =set_pitch= and =set_pan= are queued for the thread, so they never wait on a decode or on raylib's lock |
| Getters | =grl_music_is_playing()= and =grl_music_get_time_played()= return what the thread last published, or what the last queued call will leave (a seek's target, a stop's 0) until it ran; the position is at most one period (~5 ms) old |
| End of track | a non-looping music that ends is taken off the thread's list and reads as stopped within one period |
| Processors | unchanged: added and removed on the caller's thread |
| Shutdown | =grl_audio_device_close()= (and the device's finalize) applies what is queued and joins the thread before closing raylib's device |
| Lifetime | the thread holds a reference to the music's voice, not the =GrlMusic=; disposing of a music queues its unload |

The switch can change at any time; switching it on seeds the mirror with one direct read; switching it off waits for what is queued, then hands the refills back to =grl_music_update()=.  The device thread takes only raylib's lock, which is why processors and stream callbacks may not call graylib's audio functions.

Note on =looping=: raylib loads music looping; graylib now makes the loaded music follow the =looping= property, which starts =FALSE=, so a music that is never set looping now ends instead of repeating.  Call =grl_music_set_looping (music, TRUE)= for background tracks that should loop.

Tests: =tests/test-music.c= (the switch and inert calls headless; playback without =grl_music_update()=, pause, seek, end detection, stop and closing the device under a playing track with =GRL_TEST_AUDIO_DEVICE=1=).

** Complete Example
:PROPERTIES:
:CUSTOM_ID: complete-example
:END:
#+begin_src C
#include <graylib.h>

int
main (int argc, char *argv[])
{
    g_autoptr(GrlWindow) window = NULL;
    g_autoptr(GrlAudioDevice) audio = NULL;
    g_autoptr(GrlMusic) music = NULL;
    g_autoptr(GrlSound) click = NULL;
    g_autoptr(GrlColor) bg = NULL;
    g_autoptr(GError) error = NULL;

    /* Create window */
    window = grl_window_new (800, 600, "Audio Demo");
    grl_window_set_target_fps (window, 60);

    /* Initialize audio */
    audio = grl_audio_device_get_default ();
    if (!grl_audio_device_init_audio (audio))
    {
        g_printerr ("Failed to init audio\n");
        return 1;
    }

    /* Load audio files */
    music = grl_music_new_from_file ("music.ogg", &error);
    if (music == NULL)
    {
        g_print ("No music file: %s\n", error->message);
        g_clear_error (&error);
    }
    else
    {
        grl_music_set_looping (music, TRUE);
        grl_music_set_volume (music, 0.5f);
        grl_music_play (music);
    }

    click = grl_sound_new_from_file ("click.wav", &error);
    if (click == NULL)
    {
        g_print ("No sound file: %s\n", error->message);
        g_clear_error (&error);
    }

    bg = grl_color_new (30, 30, 45, 255);

    while (!grl_window_should_close (window))
    {
        /* CRITICAL: Update music stream */
        if (music != NULL)
        {
            grl_music_update (music);
        }

        /* Handle input */
        if (grl_input_is_key_pressed (GRL_KEY_SPACE))
        {
            if (music != NULL)
            {
                if (grl_music_is_playing (music))
                    grl_music_pause (music);
                else
                    grl_music_resume (music);
            }
        }

        if (grl_input_is_key_pressed (GRL_KEY_E) && click != NULL)
        {
            grl_sound_play (click);
        }

        /* Draw */
        grl_window_begin_drawing (window);
        grl_window_clear_background (window, bg);

        if (music != NULL)
        {
            gchar text[64];
            g_snprintf (text, sizeof(text), "Time: %.1f / %.1f",
                        grl_music_get_time_played (music),
                        grl_music_get_time_length (music));
            grl_draw_text (text, 20, 20, 20, NULL);
        }

        grl_draw_text ("SPACE: Play/Pause  E: Sound Effect", 20, 50, 16, NULL);
        grl_draw_fps (700, 10);

        grl_window_end_drawing (window);
    }

    return 0;
}
#+end_src

*** Callback-Based Streaming
:PROPERTIES:
:CUSTOM_ID: callback-based-streaming
:END:
Instead of pushing buffers from the game loop, a stream can let the device pull its samples from a callback on the device's own thread.  This takes synthesis off the game thread entirely and lowers latency: the device asks for small blocks just before it plays them, where a pushed stream renders a whole sub-buffer ahead.

#+begin_src C
/* runs on miniaudio's mixer thread, raylib's audio lock held */
static void
fill (gpointer buffer, guint n_frames, gpointer user_data)
{
    MySynth *synth = user_data;
    gfloat  *out = buffer;   /* the stream's format: here 32-bit float stereo */

    my_synth_render (synth, out, n_frames);
}

g_autoptr(GrlAudioStream) stream = grl_audio_stream_new (44100, 32, 2);
grl_audio_stream_set_callback (stream, fill, synth, NULL);
grl_audio_stream_play (stream);
/* ... */
grl_audio_stream_set_callback (stream, NULL, NULL, NULL);   /* detached: fill is not running and never runs again */
#+end_src

| Function | Purpose |
|----------+---------|
| =grl_audio_stream_set_callback (stream, func, user_data, destroy)= | set, replace or (with =NULL=) remove the callback; the old one is detached and its =destroy= has run when this returns |
| =grl_audio_stream_has_callback (stream)= | whether a callback fills the stream |
| =GRL_AUDIO_STREAM_MAX_CALLBACKS= (64) | streams that can have a callback at once |

- =GrlAudioStreamCallback (gpointer buffer, guint n_frames, gpointer user_data)= gets the block in the stream's own format (sample size and channels as created), at most 4096 bytes (512 frames of 32-bit stereo), several blocks back to back per device period.  It must fill every frame.
- It runs only while the stream plays (not paused or stopped).
- With a callback, =grl_audio_stream_update()= does nothing and =grl_audio_stream_is_processed()= is always =FALSE=, so an old pump loop does no work.
- With a callback, =play=, =stop=, =pause=, =resume=, =set_volume=, =set_pitch= and =set_pan= are queued for graylib's audio thread and =grl_audio_stream_is_playing()= reads its mirror ([[#audio-thread][the audio thread]]); setting, replacing or removing the callback still takes raylib's lock on the caller's thread, and removing or replacing one first waits for what is queued.
- The same rules as for processors: it runs with raylib's audio lock held, so it must not block, must not call graylib's or raylib's audio functions, and must not wait for a lock another thread holds while calling them.  Share state with the game through atomics or a queue (libregnum's synthesizers drain a command queue at the start of each block).
- How it is wired: raylib's =SetAudioStreamCallback()= has no user data, so graylib keeps a table of trampolines as for processors.  Setting fills a free slot before handing raylib its trampoline; removing hands raylib =NULL= first (under raylib's lock, so the callback is not running afterwards) and frees the slot.  A callback that cannot be detached because the device was closed under a loaded stream retires its slot.  When every slot is taken, setting logs a warning, calls =destroy= at once and leaves the stream without a callback.

Tests: =tests/test-audio-stream.c= (bookkeeping, slot reuse and exhaustion headless; the device pulling the callback and never calling it after removal with =GRL_TEST_AUDIO_DEVICE=1=).

** Per-Voice Processors
:PROPERTIES:
:CUSTOM_ID: per-voice-processors
:END:
A processor is a callback with user data that rewrites one voice's samples (a =GrlSound=, a sound alias, a =GrlMusic= or a =GrlAudioStream=) each time raylib mixes that voice into the device output: per-voice effects, sends into a submix bus, meters.  It wraps raylib's =AttachAudioStreamProcessor()= without modifying raylib.

| Function | Purpose |
|----------+---------|
| =grl_sound_add_processor (sound, func, user_data, destroy)= | add a processor after the existing ones; returns its id, 0 when no slot is free |
| =grl_sound_remove_processor (sound, id)= | remove one; once it returns the processor no longer runs and =destroy= ran |
| =grl_sound_clear_processors (sound)= / =grl_sound_get_n_processors (sound)= | remove all / count |
| =grl_sound_process (sound, frames, n_frames)= | run the processors over a block in place, as the device would (offline rendering, tests; not introspected) |
| =grl_music_*= / =grl_audio_stream_*= | the same five for music and audio streams |
| =grl_audio_processor_get_n_free_slots ()= | how many more processors can be attached |

*** The callback
=GrlAudioProcessFunc (gfloat *frames, guint n_frames, guint channels, gpointer user_data)= receives the voice's block in raylib's mixing format: interleaved 32-bit float, =GRL_AUDIO_PROCESSOR_CHANNELS= (2) channels at the device's rate, whatever the file's own format.  The samples are the voice's *before* raylib applies its volume and pan (raylib mixes them in after the processors), so a processor that needs the voice's level reads =grl_sound_get_volume()= / =grl_sound_get_pan()= itself; zeroing the block silences the voice in the mix.

On a playing voice the callback runs on miniaudio's thread with raylib's audio lock held: it must not block, must not call graylib's or raylib's audio functions, and must not wait for a lock that another thread holds while calling them.

*** How it is wired
raylib's processor is a bare =void (*)(void *, unsigned int)= without user data, and the block it is handed is a scratch buffer shared by all voices.  graylib therefore keeps a table of =GRL_AUDIO_PROCESSOR_MAX_SLOTS= (256) trampolines, each a distinct static function that knows its slot: adding a processor takes a free slot, stores the callback and data there, then attaches that slot's trampoline to the voice's raylib stream; removing detaches it first and clears the slot afterwards.  raylib's attach and detach take its audio lock, which the device thread holds while it runs the trampolines, so a slot is never seen half written.

- Processors run in the order they were added (raylib keeps a list per stream).
- A voice drops its processors when it is disposed, before it is unloaded (raylib does not free a stream's processors when it unloads the stream).
- An object without loaded audio keeps its processors; they run only through =*_process()=.  While the audio device is closed a processor is kept but not attached; a processor removed while the device is closed from a voice that stays loaded retires its slot for good (raylib still holds that trampoline on the buffer), so a voice surviving a device restart never calls another voice's processor.
- When every slot is taken, =*_add_processor()= logs a warning, calls =destroy= on the data at once and returns 0.

#+begin_src C
/* halve one voice's level before it is mixed */
static void
halve (gfloat *frames, guint n_frames, guint channels, gpointer user_data)
{
    guint i;

    for (i = 0; i < n_frames * channels; i++)
        frames[i] *= 0.5f;
}

guint id = grl_sound_add_processor (alias, halve, NULL, NULL);
/* ... */
grl_sound_remove_processor (alias, id);
#+end_src

Tests: =tests/test-audio-processor.c= (headless, on unloaded objects): order and the stereo block, removal, destroy notifies on removal, clear and dispose, the slots given back, exhaustion.

** Sound vs Music: When to Use Each
:PROPERTIES:
:CUSTOM_ID: sound-vs-music-when-to-use-each
:END:
| Feature         | GrlSound      | GrlMusic           |
|-----------------+---------------+--------------------|
| Memory          | Fully loaded  | Streamed from disk |
| Latency         | Instant       | Slight delay       |
| Best for        | Short effects | Long tracks        |
| Overlapping     | Supported     | Single instance    |
| Requires update | No            | Yes (every frame)  |

*Use GrlSound for:*

- Button clicks
- Explosions
- Footsteps
- UI feedback
- Any sound < 5 seconds

*Use GrlMusic for:*

- Background music
- Ambient sounds
- Voice overs
- Any audio > 10 seconds
